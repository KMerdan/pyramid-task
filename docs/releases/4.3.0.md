# Standalone Pyramid Task 4.3.0

This release makes existing proof reuse easier to inspect and reduces routine
output and evidence duplication. Both host manifests and runtime ship as 4.3.0
from `main`. Project format V3, plan schemas 1/2, state schema 1 and the existing
acceptance rules remain unchanged. Installing this release does not migrate a
project or accept its work.

## Behavior and limits

- `inspect --harness NODE --explain` validates current-state RUN/requirement
  pairs with the existing validator. It returns aggregate counts, at most eight
  rejection groups, explicit failure/unknown context and detail entry points.
  `--explain-page N` returns ten pairs; `--full` retains complete page text.
  Paging bounds presentation, not validation CPU or full-page bytes. Compare
  context and `scan_sha256` when joining pages.
- `detail_sources.assessment` identifies current canonical `last_result` and
  `last_audit` through a file, JSON Pointer, named fields and semantic SHA-256.
  Read the fields and verify the fingerprint before relying on them. Updates
  can replace these values; original failed results/events remain the source
  for historical failures. Legal V3 null/structured/conflicting result shapes
  are reported as unknown rather than silently treated as success.
- `inspect --audit-readiness NODE --readiness-summary` retains the complete
  computed readiness decision, counts, omissions, guards and a full-detail
  query. Ordinary queries retain their previous response contracts. Invalid
  option combinations fail before writes.
- Skill guidance requires an evidence-backed disposition of relevant failures,
  fresh observations after relevant repairs or environment changes, concrete
  review triggers and inspection refresh after relevant implementation writes.
  Reuse unaffected observations; retain required independent/human/visual review.
  Keep necessary failures and bounded results instead of repeated full mutation
  exports. Writing checks use owned disposable sparse Git worktrees.

An old RUN can still qualify after a failed audit followed by retake and an
implemented update. This inherited V3 behavior is explicitly regression-tested;
the new diagnostic is advisory and is not a failure veto. It cannot discover
unsubmitted external failures or establish their resolution. Current assessment
replacement makes the existing failure history and Skill disposition important.
No failure ledger, new hard block, V4, Git-style object store, automatic input
contraction or event encoding change is included.

## Qualification

Publication requires repository validation, the full runtime and maintainer
suites, isolated-package checks and the exact release commit's Python
3.10/3.12/3.13 CI. The GitHub Release's `release-validation.json` records actual
results, source identity and any skipped optional controls; `SHA256SUMS` covers
the downloadable archive and validation receipt. Installed-host qualification is
recorded separately after each host's native marketplace/update operation.

The retained regressions cover unchanged default responses and canonical bytes,
input/contract/artifact/dependency/inspection negatives, failure diagnostics,
legal V3 result shapes, complete assessment retrieval and drift detection, and
bounded multi-page output. Source review distinguishes the query wrapper from
unchanged eligibility/storage/history policy. No rendered viewer changes are
included, so browser/visual review is inapplicable. Model-backed agent evaluation
is outside these deterministic checks.

`tools/qualify_lean_workflow.py` supplies controlled S3 feasibility observations
and an actual pre-3.8 recovery-defect replay for A8. Its modeled policies show
that repeated executions and auxiliary copies can be avoided. They do not prove
real agent workflow convergence, token/latency gains, global productivity or net
storage savings. The historical defect is a standalone recovery control, not
production billing acceptance.

## Update and recovery

Use the repository-backed marketplace commands in the README for each host.
Verify the installed path, manifest/runtime version and source bytes independently
for Codex and Claude Code. Start a new host session for skill discovery; an
existing conversation may retain the previous skill catalog.

Retain the 4.2.2 caches and their hashes through qualification. A host install
failure can be repaired through its supported plugin commands using the known
release source; never relabel a cache or edit registries to fake an upgrade.
Because canonical formats and acceptance remain unchanged, installing alone
requires no project conversion. Any rollback after later project mutations must
still respect their normal runtime compatibility and recovery rules. Hemkar
Service, Hemkar CLI and Hemkar Skill are separate targets and are not deployed
or upgraded by this release.
