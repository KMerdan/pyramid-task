# Standalone Pyramid Task 4.3.1

This patch repairs live Observer startup and best-effort usage recording. Both
host manifests and runtime ship as 4.3.1 from `main`. V3 acceptance, plan schemas
1/2, state schema 1, usage schema 1 and the event protocol remain unchanged.
Installing this release neither migrates a project nor verifies its work.

## Behavior and limits

- Validate the initial live snapshot before acknowledging file signatures. A
  publication between snapshot capture and server construction now converges
  without requiring another mutation. Validate against the same implementation
  frontier as the publisher, retaining legitimate brownfield blockers and
  rejecting tampered projections. Preserve the last valid snapshot on errors.
- Initialize usage tables/version only for version-zero databases. Warm calls
  avoid schema writes. Each start/finish phase has a 500 ms BUSY/LOCKED retry
  budget. Retry only when non-commit or rollback is confirmed; an ambiguous
  completed commit is never replayed. Never rerun the user's command.
- Expiry remains fail-open and preserves original stdout and exit status.
  Collection can omit a start or leave a finish unrecorded. Safe warnings name
  the phase, allowlisted reason and SQLite code without raw paths or arguments.
  The lock budget is not a hard deadline on filesystem or operating-system I/O.
- Tests wait for the target version/context, preserve bounded failure details,
  and use controlled real publications, processes and SQLite locks. A test
  helper no longer shadows unittest's assertion-failure method.

## Qualification

Publication requires the exact new commit's Python 3.10/3.12/3.13 CI to pass,
repository validation, the full runtime/maintainer suites, an archive matching
Git and isolated-package checks. The release asset `release-validation.json`
records actual results, optional skips and all current failed/retried attempts.
`SHA256SUMS` covers the archive and receipt. Prior 4.3.0 first-attempt CI failures
and its successful retry remain in that release's receipt and Actions history.
The subsequent diagnosis and controlled regressions establish mechanisms; they
do not claim an exact replay of the original CI timing.

The focused controls cover startup publication, brownfield frontier/blockers,
intermediate projection failures and recovery, tamper refusal, cold/warm SQL,
start/finish contention, timeout, rollback, commit ambiguity and execution once.
Source review checks unchanged V3 acceptance and event construction. A real
browser startup observation supplements HTTP/SSE regression tests; no layout or
responsive-design claim is made. No model-backed evaluation is included.

## Update and recovery

Before updating, retain an authentic backup and digest of the installed 4.3.0
source: native marketplace updates can remove earlier caches. Use each host's
native repository-backed marketplace/update commands. Verify installed paths,
manifest/runtime versions, every plugin source file and focused regressions
separately for Codex and Claude Code. Start a fresh host session for skill
catalog discovery. An existing conversation can retain its previous catalog.

If installation fails, use supported host plugin commands with the known release
source. Do not relabel caches or edit registries to simulate an upgrade. Runtime
installation alone requires no project conversion; recovery after later project
writes must still respect normal compatibility and history rules. Hemkar
Service, CLI and Skill are separate targets and are not changed here.
