# Standalone Pyramid Task 4.2.2

This release repairs an existing-project lifecycle limitation. In 4.1.0 and
4.2.1, an existing greenfield manifest silently replaced an explicit
`new-intent --mode brownfield` request in preview and apply. This also affected
projects originally created by 4.2.1; it was not a legacy-data-only problem.

## Behavior

For an existing project, `auto` continues to inherit its manifest mode. An explicit
brownfield request now reports and hashes `mode: brownfield` plus
`mode_transition: {from: greenfield, to: brownfield}`. Apply requires the matching
approved hash and current context. The internal reset boundary revalidates that
approval before archiving; ordinary reset does not acquire a conversion flag.

The old manifest remains greenfield in its restorable archive. Existing archive
bytes, old events/reports and immutable history records are preserved. The new
intent appends its start record and receives a brownfield manifest plus incomplete
baseline/assurance placeholders. Prepared assessment and impact candidates use
normal `assess` and `impact`; audits require normal brownfield assurance coverage.
The transition does not treat placeholders as completed assessment or acceptance.

Brownfield-to-greenfield requests fail before writes. Fresh creation and existing
same-mode cycles keep their previous behavior. The preview schema gains only an
optional `mode_transition`; project format V3, plan schemas 1/2 and state schema 1
are unchanged. Both host manifests and executable runtime are 4.2.2.

## Verification

The ten new lifecycle regressions cover explicit preview/apply agreement,
mode/candidate stale-hash refusal without writes, internal-reset approval
revalidation, completed-project archive and prior ledger record preservation,
byte-identical reuse of an existing archive, auto inheritance for both modes,
baseline carry-over, downgrade refusal, a real schema-2 CLI successor, and normal
assessment/impact/audit enforcement. They supplement the retained 235 runtime
regressions and 17 maintenance tests.

A separate owned fixture is created and closed with the cached native 4.1.0
runtime. The fixed CLI previews and applies a schema-2 brownfield successor,
validates it, inspects ready work, and performs normal assess/impact. The same
fixture's auto-mode preview hash is identical under native 4.1.0 and the fixed
runtime. The old installation's source files remain unchanged. These synthetic
fixtures establish runtime transitions, not product tests, human acceptance or
agent workflow success.

Repository validation, the full local suite, isolated-package checks and the
release commit's Python 3.10/3.12/3.13 CI are required before publication. Exact
results and source identity accompany the GitHub Release in
`release-validation.json`; optional ast-grep absence is reported separately from
failures. The skill-creator quick validator could not run in the local environment
because PyYAML is absent; the repository's stdlib guidance validator and its
maintenance tests cover the supported metadata profile without a new dependency.

No rendered viewer source changes, so visual/browser review is not applicable to
this repair. No external model evaluation is needed for the deterministic mode
transition. This release does not implement the separately discussed React
visualization dashboard.

## Use and recovery

Update the repository-backed marketplace and plugin through each host. Use the
new version's absolute runtime path, and start a new host session for discovery.
Do not relabel an old cache or hand-edit plugin registries/project manifests.
Installation alone does not execute a project transition.

For a greenfield successor, regenerate the preview with `--mode brownfield` and
review its hash and preserved-state summary. An old preview that reported
`greenfield` does not approve a brownfield conversion. Run apply only with its
matching preview, then normal assessment/impact and validation.

Before apply, a fresh preview is read-only and can be discarded. Apply preserves a
restorable old-intent archive and append-only history; use supported lifecycle
recovery with actual authority rather than editing files or discarding later
writes. Previous plugin caches are retained and hash-checked during this update.
The actual Hemkar canonical transition is explicitly outside this repair/update;
its canonical, planning and evidence file hashes are checked for preservation.
