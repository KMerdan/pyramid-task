# Conditional goal-prompt boundaries

Use only sections that change this project's decisions. These are drafting rules,
not grants, commands, qualifications or a universal runtime checklist.

## Browser and visible behavior

Name the existing capture procedure and owned profile/fixture, if verified.
Require real route/state captures at the task's relevant viewports, actual image
inspection, repair and affected retest. Keep behavior, capture and visual judgment
separate. Authentication state and personal browser profiles require their own
authority. Missing tooling is a setup/acceptance gap, not a successful visual
check or permission to install software. Do not duplicate a working Playwright,
browser-use or DevTools harness just because another tool is available.

## Disposable guest or host-sensitive work

Include guest operations only when the current outcome needs them. Identify owned
seed/clone, test account, procedure, guest/host paths, isolation/network boundary,
qualification and cleanup checks. Use synthetic credentials where authorized.
Never copy the example's Electron/VM permission to an unrelated project.

Separate ordinary authorized guest work from personal host configuration,
Keychain/accounts/profiles, installed apps, privileged software, services/network
changes and newly exposed host files. New sensitive transfers or business effects
require explicit authority. Ownership/isolation/cleanup uncertainty stops the
affected operation. Keep unrelated safe work available. An unknown qualification
blocks a consequential procedure even if its user permission is established.

## Artifact growth

Reuse a lightweight existing inventory before creating a new file. Record owner,
purpose, size, candidate identity, retention and active work/handoff/recovery/proof
references. Prefer shared immutable packages/runtimes/snapshots when safe. A guard,
report directory or task owner changing does not justify a full extra copy.

Propose a working budget from observed sizes and the next required run. Report
retained exceptions at task/gate checkpoints. If no inventory exists, request an
inventory/budget proposal as the first relevant storage step; do not fabricate a
size, invent registered roots or promise cleanup of everything beyond a number.

Normally one current and one useful previous large candidate may suffice; one
clean VM seed and active clones apply only to VM projects. References, recovery,
canonical history and unresolved failure evidence override those defaults.

Include automatic cleanup only if the human already authorizes it and a supported
procedure exists. Otherwise list it as proposed authority outside the prompt.
Require positively identified owned disposable resources, stopped processes/VMs,
no active/recovery/proof references, exact registered artifact roots and retained
reports/captures/provenance. Never follow untrusted links or apply broad recursive
deletion to supplied paths. Uncertain/failed cleanup is not permission to retry
deletion. Stop that operation and report the specific pending need.
