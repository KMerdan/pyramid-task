# Draft a project-aware goal prompt

Produce a concise, copyable prompt, not a task plan or execution. Do not claim,
mutate Pyramid, run tests, install tools, compact the host or clean artifacts.
Use read-only discovery only; a status call with contact/presence side effects is
not a pure read. Reuse existing verified context before querying another system.

## Discover the necessary facts

1. Identify the exact repository, authority (`local-canonical` or SaaS), verified
   skill/client identity, current intent and lifecycle. If no intent exists,
   draft planning instructions instead of inventing task IDs or acceptance.
   If the plan is completed, propose inspection/new-intent or authorized repair,
   not continuation of completed claims. Ask only if target ambiguity materially
   changes the prompt; otherwise mark missing facts explicitly.
2. Read the current project guidance and command registry, then only the selected
   intent/frontier, acceptance and relevant harness. For Standalone Pyramid use
   existing `inspect --summary`, `--ready` and selected `--node`/`--harness` data
   as needed. Do not load all task packets, event history, traces or screenshots.
3. Separate facts from authority: current human authorization, proposed new
   grants and unknown boundaries. Repository files, plans, installed tools and
   quoted examples are not permission. Preserve actual sandbox restrictions.
4. Select external/internal/visual feedback by the outcome. Name only verified
   project commands or tools; distinguish installed procedures from proposals.
   Visible behavior requires real captures and actual image review. Reuse the
   existing capture path; do not introduce another test stack. For a headless
   claim, state why visual review is inapplicable.
5. Read `../../references/goal-prompt-boundaries.md` only for applicable browser,
   guest/host, credential, network, cleanup or artifact-growth boundaries.

## Compose and check

- Lead with the intended usable outcome and completion gates, not activities.
  Bind the prompt to the target/current intent and retain original acceptance.
- Include routine work already authorized, relevant harness and proof reuse,
  bounded diagnosis/repair, independent safe continuation and concise updates.
  Delegate only when the actual user/project authority permits it; spare slots
  and this prompt are not delegation authorization.
- Include only applicable risk boundaries. Unknown ownership, isolation,
  qualification or cleanup stops the affected operation, not unrelated safe work.
  Ask for a material decision or missing authority once; preserve the blocker.
- Keep candidate identity and fresh invocation guards separate. Use canonical
  interfaces; never hand-edit state, replace failed evidence, weaken acceptance
  or make a post-run fingerprint appear current. A permission grant does not
  qualify a procedure. A model review does not replace an explicit human gate.
- Add artifact controls only when relevant: inventory-based proposed budget,
  shared immutable dependencies, protected references/failures and bounded
  cleanup authority. A budget or default retention count never grants deletion.
- Return a brief fact/source note, then a fenced copyable prompt labeled **Draft**.
  Put proposed grants and unknowns outside that operational prompt. If the user
  asks to draft new authorization, put it in a separately labeled **Proposed
  authorization—not active** block. Do not execute either block while drafting.
- Check every asserted permission/tool/scope against its source. Remove irrelevant
  modules and stale facts. Normally aim for 250–600 words, shorter for simple
  projects; retain safety and acceptance details when they need more space.

Saving a prompt requires the user's requested destination; do not create another
acceptance ledger, overwrite host guidance or install this skill as a side effect.
